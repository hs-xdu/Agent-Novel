# AI 网文写作 Agent MVP 技术方案

版本：V0.1

日期：2026-11-23

依据：[MVP 设计文档](MVP设计文档.md)

## 1. 目标与适用范围

本方案确定第一版的技术选型、模块边界和关键实现原则，用于指导后续开发。验收目标是：用户能够完成小说设定与大纲，连续创作至少 5 章，经审阅定稿后更新长期记忆，并在重启后继续创作。

第一版面向本地单用户，采用单进程应用和单主 Agent 工作流。用户确认是设定生效、章节定稿的必要条件。暂不引入多 Agent、向量数据库、自动发布、云同步或分布式任务系统。

## 2. 技术栈

| 部分 | 选型 | 用途与边界 |
|---|---|---|
| 开发语言 | Python 3.12 | 作为初始开发基线，实际兼容性在安装依赖时验证 |
| 本地 Web UI | NiceGUI | 项目管理、设定编辑、章节编辑和生成进度展示 |
| 数据模型 | Pydantic 2 | 校验项目、人物、大纲、章节元数据及记忆结构 |
| 模型接入 | 所选厂商官方 Python SDK | 第一版实现一个提供方，通过应用内部接口隔离调用细节 |
| Agent 编排 | Python 服务函数和显式状态流转 | 串联上下文准备、模型生成、用户确认和持久化 |
| 数据存储 | Markdown + JSON | 正文和长文本用 Markdown，结构化数据用 JSON |
| 环境与依赖 | uv + pyproject.toml + uv.lock | 声明依赖并锁定可复现环境 |
| 自动测试 | pytest | 核心流程、文件安全、模型异常及恢复测试 |
| 日志 | Python logging | 记录操作、错误和任务状态 |

NiceGUI 已基于 FastAPI，第一版直接调用 Python 服务层，不额外维护独立前端工程和内部 HTTP 调用。需要对外 API 时，再按实际需求增加端点。[NiceGUI 技术基础](https://nicegui.io/documentation/section_foundations)

模型厂商与具体模型尚未确定。接入前用中文创作、结构化记忆提取和上下文长度做小规模验证，再确定单一提供方；本方案不预设不同厂商的兼容接口具备相同能力。

依赖在开发启动时解析并提交锁文件，不在本方案中指定未经验证的最新版本。按原设计要求，从锁文件导出 requirements.txt，避免维护两套依赖清单。[uv 导出说明](https://docs.astral.sh/uv/reference/cli/#uv-export)

## 3. 应用结构与职责

调用关系：NiceGUI 界面 → 应用工作流 → 模型适配、记忆服务与存储服务。

| 模块 | 职责 |
|---|---|
| app/ | 应用入口、页面、会话状态和用户交互 |
| agent/ | 设定生成、大纲生成、章节生成及定稿流程 |
| llm/ | 模型调用接口、提供方实现、超时及错误转换 |
| prompts/ | 按任务组织提示词模板 |
| models/ | Pydantic 数据模型及业务校验 |
| memory/ | 记忆提取、上下文选择、冲突检查与历史检索 |
| storage/ | 项目目录、文件读写、修订保存与恢复 |
| tests/ | 单元测试、集成测试和故障恢复测试 |
| docs/ | 产品设计、技术方案和后续操作说明 |

界面不直接写文件；模型输出也不直接落入正式数据。核心服务保持可脱离界面测试，方便后续替换 UI 或模型提供方。

小说数据存放在独立的 projects/ 目录，每个项目使用唯一 project_id。运行数据、本地密钥、日志和虚拟环境排除在源码 Git 仓库之外。

## 4. 界面与生成任务

界面按设计文档划分为项目管理、设定与大纲、章节创作、小说记忆四个区域。第一版正文采用纯文本编辑，支持 Markdown 预览；专业排版和复杂富文本暂缓。

选中段落修改需先做交互验证：记录选区位置及正文修订号，AI 返回替换建议，由用户确认应用。若生成期间原文发生变化，提示重新选择，避免按过期位置替换。

模型请求使用异步调用，避免长时间生成阻塞界面；必要的同步 I/O 使用后台线程。NiceGUI 提供相关 I/O 任务支持。[NiceGUI 任务说明](https://nicegui.io/documentation/section_action_events)

每个项目同一时间只允许一个改变正式状态的操作。生成任务绑定 project_id、章节编号和输入修订号，切换项目后结果仍归属原任务。重复点击不启动重复任务，过期结果不能覆盖较新的编辑内容。

生成内容先显示为候选结果，用户保存后形成草稿。展示进行中、失败、已保存等状态；页面断开或任务取消后保留已保存草稿，不承诺恢复尚未保存的流式片段。

## 5. 数据模型与文件组织

沿用设计文档中的 settings/、outline/、chapters/ 和 memory/ 结构，在此基础上补充草稿、修订和操作状态目录。

- 项目、人物、分卷和章节使用稳定 ID；人物关系引用 ID，避免同名导致关联混乱。
- JSON 包含 schema_version；章节元数据包含章节编号、状态、修订号及正文位置。
- 正式设定与候选设定分开保存，大纲同样记录确认状态。
- 草稿与正式章节分开保存；整章重新生成保留已有正式版本。
- 正式记忆记录来源章节及其修订号，支持追溯提取依据。

Pydantic 负责结构与字段校验，服务层负责跨文件业务约束，例如人物引用是否存在、章节是否属于当前项目。通过模型校验不代表剧情事实正确，事实冲突仍需结合来源及用户判断。

文件统一 UTF-8，章节按数字编号排序，不按文件名字典序推断顺序。输入路径限制在所属项目目录内，项目标题不直接作为可信文件路径。

## 6. 单 Agent 创作流程

设定和大纲采用“生成候选 → 编辑审阅 → 确认保存”的流程，用户未确认前不替换正式版本。

章节创作采用以下流程：

1. 校验正式设定、关联大纲和项目记忆状态。
2. 选择本章所需的上下文，形成固定输入快照。
3. 调用模型生成正文，展示候选结果。
4. 用户编辑、重新生成或保存草稿。
5. 用户确认定稿，保存正式正文修订。
6. 提取并校验记忆候选，发布新的正式记忆快照。

章节业务状态仍为“草稿、已定稿”；记忆同步状态另行记录为“待更新、更新中、已同步、更新失败”，避免将模型失败误认为正文未保存。

已定稿章节再次编辑时创建草稿修订。若用户重新定稿历史章节，标记该章及后续相关记忆需要重建；已有后续章节正文保留并提示复核。第一版按章节顺序从变更位置重建记忆，不承诺自动修正后续正文。

## 7. 模型接入与上下文组织

模型适配层区分自由文本生成和结构化提取，对上层统一提供正文、提取结果与错误信息。API 地址、模型名称、超时和生成参数可配置，API Key 通过环境变量读取。

结构化提取优先使用提供方支持的结构化输出能力，再由 Pydantic 校验。对于不支持或校验失败的返回，限制纠错重试次数，失败后保留原始响应供诊断，不写入正式记忆。

网络超时、限流和暂时性服务错误采用有限重试及退避；认证错误直接提示配置问题。重试统一由适配层管理，避免 SDK 与业务层叠加重试。记录请求标识、耗时和可用的用量信息，不记录密钥。

上下文由以下内容按预算组合：

- 已确认的核心世界规则、全书及当前分卷摘要。
- 当前章节大纲和用户额外要求。
- 本章相关人物状态、关系及未回收伏笔。
- 最近章节摘要、必要的前章结尾。
- 根据人物、事件和关键词检索出的历史正文片段。

第一版采用结构化筛选和关键词检索。为输出预留空间，超出预算时优先缩减历史片段与较远摘要；必要设定仍放不下时明确提示，避免静默截断。中文字符数与 token 数分别处理，目标字数仅作为生成约束与结果提示，不假设模型必然精确满足。

## 8. 长期记忆与数据可靠性

记忆分为世界观、人物、剧情和伏笔四类。正式设定作为约束，章节记忆作为事实记录；模型提取的变更以候选形式校验后发布。与已确认规则冲突时保留候选并提示用户处理，不自动覆盖正式设定。

单文件保存采用同目录临时文件写入、校验后替换，保留必要的上一修订。单文件替换不能提供多个文件的整体事务，定稿与记忆发布需额外处理：

1. 记录带唯一操作 ID、输入修订号和处理阶段的持久化操作日志。
2. 保存完整正式正文及章节元数据；异常中断后依据日志恢复未完成步骤。
3. 在临时区域生成并校验完整记忆快照，记录已处理的章节修订。
4. 通过单一清单指针发布已完成的记忆快照，读取端不混用不同批次的数据。
5. 记录操作完成；重复恢复同一操作不会重复追加剧情事件。

启动时检查未完成操作。正文已保存但记忆生成失败时保留正文，允许用户重试；记忆同步前阻止后续章节的 AI 生成，仍允许查看和编辑。重试使用已定稿正文，无需再次确认定稿或重复生成正文。

同一项目通过进程内锁串行写入。第一版仅支持一个应用进程写入同一项目，启动时检测重复实例或目录占用；外部编辑导致的修订变化应提示冲突。原始章节始终保留，摘要和快照不能替代正文备份。

## 9. 配置、运行与日志

应用默认仅监听 127.0.0.1，以本地浏览器访问。配置分为运行环境配置和小说项目配置，后者不包含模型密钥。

开发使用 uv sync 安装锁定依赖，通过 uv run 启动应用及测试；具体入口命令在实现时写入 README。交付同时提供从锁文件导出的 requirements.txt。

日志包含项目 ID、章节 ID、操作 ID、阶段及错误类别。默认不输出完整小说正文和提示词；需要诊断时显式开启本地调试记录。界面错误信息提供可执行的重试或修复入口。

## 10. 测试与验收

开发测试使用 pytest，模型调用通过可控替身返回成功、超时、非法结构和冲突结果，常规测试不依赖真实 API。

| 测试范围 | 关键验证 |
|---|---|
| 项目与存储 | 多项目隔离、UTF-8、编号排序、保存重载和路径边界 |
| 生成与编辑 | 候选不覆盖正式内容、重写保留修订、过期结果不覆盖新编辑 |
| 章节定稿 | 仅用户确认后定稿、重复操作幂等、草稿不进入正式记忆 |
| 记忆更新 | 来源可追溯、人物引用有效、冲突不覆盖设定、历史修改触发重建 |
| 故障恢复 | 各保存阶段注入异常，验证重启恢复、旧快照可读和重试不重复追加 |
| 界面流程 | 创建项目、编辑、生成、保存、定稿和错误重试 |

真实模型另做小规模集成测试，检查接口能力和中文结果。最终人工连续创作至少 5 章，复核人物、世界规则、事件和伏笔的一致性，并验证重启后继续创作。自动测试通过不能替代小说质量验收。

每次变更更新相应测试，交付前通过测试和验证并创建对应 Git commit。当前文档阶段运行已有 PowerShell 文档检查；Python 应用建立后增加 pytest 测试入口。

## 11. 开发顺序与待验证项

按四个阶段推进，每阶段完成可演示且可测试的结果：

1. 建立工程、配置、数据模型和文件存储，完成项目创建、编辑和重载。
2. 验证 NiceGUI 正文编辑及选区修改，接入一个模型，完成设定、大纲和章节草稿流程。
3. 完成定稿、记忆提取、快照发布、失败恢复和基础历史检索。
4. 完成五章连续创作验收、Markdown 导出、README 和依赖清单。

开发初期优先验证三个不确定点：NiceGUI 的选区编辑体验、候选模型的中文创作与结构化提取能力、文件快照在异常中断后的恢复可靠性。

若后续需要专业编辑器交互，再评估独立前端；若多进程写入和复杂查询成为需求，再评估 SQLite；若工作流出现大量分支与暂停恢复需求，再评估专门的 Agent 编排框架。升级依据实际问题决定。
